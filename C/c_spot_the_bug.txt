# Format: Front[TAB]Back
# One card per README bullet. Each front shows a snippet/scenario; the back names the bug and the fix.

# 3.1 Memory Errors
Spot the bug: `free(p); printf("%d", *p);`	Use-after-free: `p` is dereferenced after its memory was released — undefined behavior (the memory may be reused or unmapped). Fix: don't use `p` after `free`, and set `p = NULL;` so accidental reuse crashes deterministically.
Spot the bug: `free(p); free(p);`	Double free: freeing the same pointer twice corrupts the allocator's metadata and is exploitable. Fix: free once and set `p = NULL;` afterward — `free(NULL)` is a well-defined no-op, so a redundant free becomes harmless.
Spot the bug: `int *p; *p = 5;`	Uninitialized-pointer dereference: `p` holds indeterminate garbage, so the write corrupts random memory (UB). Fix: point it at valid storage first — `int x; int *p = &x;` or `int *p = malloc(sizeof *p);` (then check for `NULL`).
Spot the bug: `char buf[8]; strcpy(buf, "much too long");`	Stack buffer overflow: the source plus `\0` exceeds the 8-byte array, overrunning the stack (potentially the return address). Fix: size the buffer to the data or bound the copy — `snprintf(buf, sizeof buf, "%s", src);`.
Spot the bug: `char *p = malloc(n); memcpy(p, src, n+1);`	Heap buffer overflow: writing `n+1` bytes into an `n`-byte allocation overruns the block, corrupting heap metadata or a neighbor. Fix: allocate enough (`malloc(n+1)`) or copy only `n` bytes.
Spot the bug: `p = malloc(n); if (error) return; free(p);`	Memory leak: the early `return` skips `free(p)`, and the only pointer is lost. Fix: free before returning on every path, or use a `goto cleanup;` that frees once at the end.
Spot the bug: `p = realloc(p, n);` used directly	If `realloc` fails it returns `NULL`, overwriting (and leaking) the still-valid original block, then likely dereferencing `NULL`. Fix: `tmp = realloc(p, n); if (tmp) p = tmp; else handle_error();`.
Spot the bug: `int *f(void){ int x = 42; return &x; }`	Returning the address of a local: `x`'s lifetime ends at return, so the caller gets a dangling pointer into reclaimed stack (UB). Fix: return by value, allocate on the heap, or use a `static`/caller-supplied buffer.
Spot the bug: `for (int i = 0; i <= n; i++) a[i] = 0;` for `int a[n]`	Off-by-one: valid indices are `0..n-1`, but `i <= n` writes `a[n]`, one past the end — an out-of-bounds write. Fix: use `i < n`.
Spot the bug: `void f(int *arr){ int k = sizeof(arr)/sizeof(arr[0]); }`	`sizeof` on a decayed pointer: inside the function `arr` is a pointer, so `sizeof(arr)` is the pointer size, giving the wrong element count. Fix: pass the length as a separate parameter; `sizeof` only yields array size where the array is declared.
Spot the bug: `char *p = "hi"; free(p);`	Freeing memory not from `malloc`: `p` points at a string literal (static storage), and freeing a non-heap pointer (or an interior/stack pointer) is undefined behavior. Fix: only `free` pointers returned by `malloc`/`calloc`/`realloc`.
Spot the bug: allocating with a custom pool allocator but releasing with plain `free`	Mismatched allocator/deallocator: memory must be returned to the same allocator that produced it; mixing them corrupts both heaps (UB). Fix: pair `pool_alloc` with `pool_free`, `malloc` with `free`, `new`/`new[]` appropriately, etc.

# 3.2 String & Format Bugs
Spot the bug: `char d[5]; strncpy(d, "hello", 5); printf("%s", d);`	Missing terminator: `strncpy` copies exactly 5 chars and writes no `\0`, so `printf("%s")` reads past the buffer. Fix: reserve room and terminate — `char d[6]; strncpy(d, src, 5); d[5] = '\0';`.
Spot the bug: `char buf[64]; gets(buf);`	`gets` has no bounds check and overflows `buf` for any input longer than 63 chars — it was removed from C11 for this reason. Fix: `fgets(buf, sizeof buf, stdin);`.
Spot the bug: `printf(msg);` where `msg` is user input	Format-string vulnerability: `%` sequences in `msg` are interpreted, leaking memory (`%x`/`%s`) or writing it (`%n`). Fix: `printf("%s", msg);` — always use a literal format with untrusted data.
Spot the bug: `scanf("%s", name);` for `char name[32]`	Unbounded read: `%s` copies until whitespace with no size limit, overflowing `name`. Fix: bound the field width to one less than the buffer — `scanf("%31s", name);`.
Spot the bug: `long x = ...; printf("%d", x);`	Format/type mismatch: `%d` expects `int`, but a `long` is passed — UB, and it prints wrong values where `long` is wider. Fix: `printf("%ld", x);` (and `%u` for an `unsigned`).
Spot the bug: `char buf[16]; sprintf(buf, "%s-%d", name, id);`	`sprintf` overflow: with no size limit, a long `name` overruns `buf`. Fix: `snprintf(buf, sizeof buf, "%s-%d", name, id);` and check the return for truncation.
Spot the bug: `strtok("a,b,c", ",");`	Modifying a string literal: `strtok` writes `\0` over delimiters, but the literal is read-only memory (UB). Fix: tokenize a writable copy — `char s[] = "a,b,c"; strtok(s, ",");`.
Spot the bug: `if (s1 == s2) puts("equal");` for two `char*`	Comparing pointers, not contents: `==` tests whether they hold the same address, not whether the strings match. Fix: `if (strcmp(s1, s2) == 0)`.
Spot the bug: `char *d = malloc(strlen(s)); strcpy(d, s);`	Off-by-one allocation: `strlen` excludes the `\0`, so `strcpy` writes one byte past the buffer. Fix: `malloc(strlen(s) + 1)`.

# 3.3 Pointer & Type Bugs
Spot the bug: `int *p = arr; p += sizeof(int);`	Wrong arithmetic units: `p += sizeof(int)` advances by `sizeof(int)` *elements* (e.g. 16 bytes for a 4-byte int), not one int. Fix: to move one element use `p += 1`; pointer arithmetic is already scaled by the element size.
Spot the bug: reading a `short` via `*(short*)(charbuf + 1)`	Alignment + strict-aliasing violation: `charbuf+1` may be misaligned for a `short`, and reading `char` bytes through a `short*` breaks aliasing rules (both UB). Fix: `short v; memcpy(&v, charbuf + 1, sizeof v);`.
Spot the bug: `void *p = base; p++;`	`void*` arithmetic is illegal in standard C (`void` has no size); it only compiles as a GCC byte-sized extension. Fix: cast to a concrete type — `char *cp = base; cp++;`.
Spot the bug: `const int c = 5; *(int*)&c = 6;`	Casting away `const` and writing: modifying an object defined `const` is undefined behavior (it may reside in read-only memory). Fix: don't cast away const to write; if it must change, it should not be `const`.
Spot the bug: `if (ptr_a < ptr_b)` for pointers into different objects	Pointer comparison across objects: ordering pointers that don't point into the same array (or one-past-end) with `<`/`>` is undefined behavior. Fix: only order pointers within one object; use `==`/`!=` otherwise, or compare `uintptr_t` values if you truly must.
Spot the bug: `FILE *fp = fopen("f","r"); fread(buf, 1, n, fp);` with no check	Null-pointer dereference: `fopen` returns `NULL` on failure, and passing it to `fread` is UB. Fix: `if (!fp) { perror("fopen"); return; }` before using it. (Same applies to unchecked `malloc`.)
Spot the bug: `int *p = (int *)42;`	Integer-to-pointer cast without `intptr_t`: an arbitrary integer cast to a pointer may not round-trip or be validly usable on all platforms/alignments. Fix: use `intptr_t`/`uintptr_t` for pointer↔integer conversions, and only convert values that came from real pointers.
Spot the bug: `int n = sizeof(int *);` when the array element size was intended	`sizeof` type confusion: `sizeof(int *)` is the pointer size (e.g. 8), not `sizeof(int)` (4). Fix: apply `sizeof` to the intended type/expression — `sizeof(int)` or `sizeof arr[0]` — matching what you're measuring.
Spot the bug: `((void(*)(int))fp)(5);` when `fp` is `void(*)(double)`	Function-pointer type mismatch: calling through an incompatible signature is UB even if it seems to work — argument passing/return conventions may differ. Fix: only call through a pointer whose type matches the function's actual signature.

# 3.4 Integer & Arithmetic Bugs
Spot the bug: `int x = INT_MAX; x++;`	Signed integer overflow: incrementing past `INT_MAX` is undefined behavior (not guaranteed to wrap, and the optimizer assumes it can't happen). Fix: check first (`if (x < INT_MAX) x++;`) or use an unsigned type if wraparound is intended.
Spot the bug: `unsigned x = 0; x--; if (x < 0) ...`	Always-false condition: unsigned values are never negative; `x--` wraps to `UINT_MAX`, not below 0. Fix: use a signed type if you need negatives, or test the wraparound explicitly (`if (x > SOME_MAX)`).
Spot the bug: `long big = ...; int n = big;`	Truncation on assignment: storing a `long` into `int` silently drops the high bits when the value exceeds `int`'s range. Fix: keep the wider type, or check the value fits (`big >= INT_MIN && big <= INT_MAX`) before narrowing.
Spot the bug: `char c = 0xFF; int i = c;`	Sign-extension pitfall: where plain `char` is signed, `0xFF` is −1, so `i` becomes −1, not 255. Fix: use `unsigned char` (or `(unsigned char)c`) when treating bytes as 0–255 values.
Spot the bug: `int q = a / b;` with `b` from input	Division by zero: if `b` is 0 the `/` (or `%`) is undefined behavior (often a `SIGFPE` crash). Fix: check `if (b == 0) handle_error();` before dividing with any variable denominator.
Spot the bug: `int r = INT_MIN / -1;`	Overflow via division: `-INT_MIN` is not representable in `int`, so `INT_MIN / -1` (and `INT_MIN % -1`) is undefined behavior despite looking safe. Fix: special-case `INT_MIN`/`-1` before dividing.
Spot the bug: `uint32_t y = x << 32;` for a 32-bit `x`	Shift out of range: shifting by an amount ≥ the type's width (or negative) is undefined behavior. Fix: keep the shift count in `[0, width-1]`; if you need "shift by width", handle it as a separate case (result 0).
Spot the bug: `int x = -1; int y = x << 1;`	Left shift of a negative value is undefined behavior in C. Fix: do bit-shifting on unsigned types (`unsigned`/`uint32_t`), where shifts are well-defined modular operations.
Spot the bug: `int n = -1; if (n < sizeof(arr)) ...`	Signed/unsigned comparison: `sizeof` is unsigned, so `n` is converted to a huge unsigned value and the check passes unexpectedly. Fix: compare with a signed length, or cast carefully after validating `n >= 0`.
Spot the bug: `buf = malloc(count * size);` with untrusted `count`	Integer overflow → undersized allocation: `count * size` can wrap `size_t` to a small value, so the buffer is too small and later writes overflow the heap. Fix: check `if (count > SIZE_MAX / size) fail();` or use `calloc(count, size)`.

# 3.5 Floating-Point Bugs
Spot the bug: `total = 0.1 + 0.2; if (total == 0.3) ...`	Exact float comparison fails: `0.1 + 0.2` is not exactly `0.3` in binary floating point. Fix: compare within a tolerance — `if (fabs(total - 0.3) < 1e-9)`.
Spot the bug: summing a million small `float`s into a `float` accumulator	Accumulated rounding error: `float`'s ~7 digits of precision degrade badly over many additions, and small terms get lost. Fix: accumulate in `double`, or use Kahan (compensated) summation.
Spot the bug: `if (x == x) ok();` used to validate `x`	NaN comparison: if `x` is `NaN`, `x == x` is false (NaN is unordered), so this rejects valid-looking data or is a confusing NaN test. Fix: use `isnan(x)` to test for NaN explicitly.
Spot the bug: `float avg = 1 / 2;`	Integer division before conversion: `1 / 2` computes in `int` = 0, then converts to `0.0f`. Fix: make an operand floating point — `1 / 2.0` or `(float)a / b`.
Spot the bug: `float f = some_double_expression;`	Silent `double`→`float` narrowing: assigning a `double` result to a `float` loses precision (and may overflow to infinity). Fix: keep the value as `double` if the precision matters, or narrow deliberately and knowingly.
Spot the bug: a float result differs between `-O0` and `-O2` builds	Excess intermediate precision / FMA contraction: the compiler may keep intermediates in wider registers or fuse multiply-add, changing rounding across optimization levels. Fix: don't rely on exact float equality; use `-ffp-contract=off` or tolerances if reproducibility is required.

# 3.6 Control Flow Bugs
Spot the bug: a `switch` with work in `case 1:` and no `break` before `case 2:`	Unintended fall-through: after `case 1` execution continues into `case 2`'s body. Fix: add `break;` at the end of each case (or annotate deliberate fall-through with `[[fallthrough]]`).
Spot the bug: `if (x > 0); { do_thing(); }`	Stray semicolon: `if (x > 0);` has an empty body, so the following block runs unconditionally. Fix: remove the `;` — `if (x > 0) { do_thing(); }`.
Spot the bug: `if (x = 0) ...`	Assignment in a condition: `x = 0` assigns 0 (and is false), so the branch never runs and `x` is clobbered. Fix: use `==` for comparison — `if (x == 0)`; compilers warn with `-Wall`.
Spot the bug: `char c; while ((c = fgetc(fp)) != EOF) ...`	`EOF` truncation: storing `fgetc`'s result in a `char` loses the ability to distinguish `EOF` (−1) from byte `0xFF`, so the loop may never end or end early. Fix: use an `int` to hold the result.
Spot the bug: nested loops each declaring `int i` in the inner block	Shadowing: the inner `int i` hides the outer loop's `i`, so updates don't reach the outer counter and it misbehaves. Fix: use distinct names (`i`, `j`) or don't redeclare.
Spot the bug: `do { if (skip) continue; work(); } while (cond);`	Surprising `continue`: in a `do-while`, `continue` jumps to the condition test at the bottom, not the top — so `work()` is skipped but the loop still re-evaluates `cond`. Fix: understand it re-tests the condition; restructure with a flag/`if` if you meant otherwise.
Spot the bug: `if (a) if (b) x(); else y();` — which `if` owns the `else`?	Dangling `else`: `else` binds to the nearest unmatched `if` (the `if (b)`), regardless of indentation, so `y()` runs when `a` is true and `b` is false. Fix: use explicit braces to make the intended pairing clear.

# 3.7 Operator & Precedence Bugs
Spot the bug: `if (flags & MASK == 0)`	Precedence: `==` binds tighter than `&`, so this is `flags & (MASK == 0)`, not the intended `(flags & MASK) == 0`. Fix: parenthesize — `(flags & MASK) == 0`.
Spot the bug: `x = a == b;` when a comparison result wasn't intended	Assignment-vs-equality confusion: this assigns the boolean `(a == b)` to `x`. If you meant to test equality, it's `if (x == (a == b))` or similar; if you meant `x = a = b`, that's different. Fix: write what you mean and enable `-Wall` to catch suspicious assignments.
Spot the bug: `int y = cond ? a : b + 1;`	Ternary precedence: `?:` is lower than `+`, so this parses as `cond ? a : (b + 1)`, not `(cond ? a : b) + 1`. Fix: add parentheses to force the intended grouping.
Spot the bug: relying on `x + 1 << 2` meaning `x + (1 << 2)`	Shift precedence: `<<` is *lower* than `+`, so it is `(x + 1) << 2`, not `x + (1 << 2)`. Fix: parenthesize the intended grouping rather than trusting memory of the precedence table.
Spot the bug: `*p++` when you meant to increment the value	Increment/dereference order: `*p++` increments the pointer and yields the old `*p`; the pointee is unchanged. Fix: to increment the pointed-to value use `(*p)++`.
Spot the bug: `if (a & b)` where a logical test was intended	Bitwise-for-logical swap: `&` does a bitwise AND (no short-circuit, different result) where `&&` was meant. Fix: use `&&`/`||` for logical conditions; reserve `&`/`|` for bit manipulation.

# 3.8 Preprocessor & Macro Bugs
Spot the bug: `#define SQUARE(x) x*x` used as `SQUARE(a+1)`	No parentheses: expands to `a+1*a+1` = `a + a + 1`, not `(a+1)²`. Fix: `#define SQUARE(x) ((x)*(x))` — parenthesize each parameter and the whole expansion.
Spot the bug: `#define MAX(a,b) ((a)>(b)?(a):(b))` used as `MAX(i++, j++)`	Double evaluation: the winning argument is evaluated twice, so `i`/`j` increments more than intended. Fix: use an inline function (each argument evaluated once) or a statement-expression with temporaries.
Spot the bug: a header with type definitions but no include guard, included twice	Redefinition errors: the types get processed twice in one translation unit. Fix: wrap it in `#ifndef HDR_H / #define HDR_H / ... / #endif` or use `#pragma once`.
Spot the bug: `#define max(a,b) ...` in a file that also includes `<sys/param.h>`	Macro name collision: `<sys/param.h>` may also define `max`, causing a redefinition warning/error or subtly different behavior. Fix: use a unique/prefixed name (`MYLIB_MAX`) or `#undef` before redefining.
Spot the bug: `#define BOOL int` then comparing a `BOOL` with `true`/`false`	`#define` used as a type: it inconsistently mixes with `<stdbool.h>`'s real `bool`/`true`/`false`, and gives no type safety. Fix: include `<stdbool.h>` and use `bool` rather than a macro alias.
Spot the bug: a multi-line macro whose next-to-last line is missing a trailing `\`	Missing continuation: without the backslash the macro ends early, so the remaining lines are stray code — a syntax error or silent misbehavior. Fix: end every line of a multi-line macro except the last with `\`.
Spot the bug: `#define INIT() a = 0;` used in `if (x) INIT(); else foo();`	Semicolon in the macro body: the macro's `;` plus the statement's `;` leaves a stray empty statement, so `else` fails to attach to the `if`. Fix: wrap multi-statement macros in `do { ... } while (0)` (no trailing semicolon).

# 3.9 Resource & File Handling Bugs
Spot the bug: `fp = fopen(...); if (error) return; fclose(fp);`	Leak on the error path: the early `return` skips `fclose`, leaking the descriptor. Fix: close before returning on every path, or `goto cleanup;` that closes `fp` once.
Spot the bug: `fclose(fp);` after buffered writes, return value ignored	`fclose` can fail while flushing (e.g. disk full), silently losing data/errors. Fix: check `if (fclose(fp) != 0) handle_error();`, especially for files you wrote.
Spot the bug: `tmpnam(name); fp = fopen(name, "w");`	TOCTOU race: between generating the predictable name and opening it, an attacker can create/symlink that path. Fix: use `mkstemp`, which atomically creates and opens a unique file, or `open` with `O_CREAT | O_EXCL`.
Spot the bug: `fgets(buf, n, fp); process(buf);` in a loop, return value ignored	Ignoring `fgets`'s result: on EOF/error it returns `NULL` and leaves `buf` with stale contents, so the loop processes old data. Fix: drive the loop by the return — `while (fgets(buf, n, fp)) process(buf);`.
Spot the bug: `fopen("data.bin", "r")` then `fread` of binary data on Windows	Text-mode on binary data: on Windows `"r"` translates `\r\n`↔`\n` and may stop at a `0x1A` byte, corrupting binary reads. Fix: open with `"rb"` for binary files.
Spot the bug: `sprintf(cmd, "rm %s", userfile); system(cmd);`	Command injection: shell metacharacters in `userfile` (e.g. `"; rm -rf ~"`) run arbitrary commands. Fix: avoid the shell — `fork`+`execv("/bin/rm", (char*[]){"rm", userfile, NULL})` — and validate the input.
Spot the bug: opening fds before `fork`/`exec` without `O_CLOEXEC`	Fd leak across `exec`: descriptors the child shouldn't have stay open in the new program, leaking resources/handles (a security concern for privileged fds). Fix: open with `O_CLOEXEC` (or set `FD_CLOEXEC` via `fcntl`) so they close on `exec`.

# 3.10 Concurrency & Signal Bugs
Spot the bug: `int done = 0;` set in a signal handler, `while (!done) {}` in main	Missing volatile/atomicity: the compiler may cache `done` in a register and never see the handler's update, or the access may not be atomic. Fix: declare `volatile sig_atomic_t done;`.
Spot the bug: calling `printf` inside a signal handler	Not async-signal-safe: if the signal interrupts another `printf`/`malloc`, internal locks/state are inconsistent → UB or deadlock. Fix: set a flag in the handler and print from the main loop, or use only async-signal-safe calls like `write`.
Spot the bug: a non-`volatile` local changed between `setjmp` and `longjmp`	`setjmp` clobbering: such a local may hold an indeterminate value after the jump back, because the compiler could have kept it in a register. Fix: mark locals relied on after the jump as `volatile`.
Spot the bug: two threads doing `global = compute();` with no synchronization	Data race on a shared global: concurrent unsynchronized writes are undefined behavior and can tear/lose values. Fix: guard access with a mutex, or make the variable `_Atomic`.
Spot the bug: two threads both executing `counter++`	Data race on a non-atomic counter: `counter++` is a read-modify-write, not atomic, so increments are lost. Fix: guard with a mutex or make `counter` an `atomic_int` and use `atomic_fetch_add`.
Spot the bug: thread A locks `m1` then `m2`; thread B locks `m2` then `m1`	Deadlock from inconsistent lock ordering: each holds one lock and waits for the other. Fix: define a global lock-ordering rule so all threads always acquire `m1` before `m2`.
Spot the bug: `if (!ready) cond_wait(&cv, &m);`	Missing predicate loop: a spurious or stolen wakeup lets execution proceed with `ready` still false. Fix: re-test in a loop — `while (!ready) cond_wait(&cv, &m);`.

# 3.11 Security Vulnerabilities & Exploitation
Spot the vulnerability: unbounded `strcpy` of user input into a fixed stack buffer	Classic stack smashing: the overflow can overwrite the saved return address, redirecting execution (to shellcode or via ROP). Fix: bound the copy (`snprintf`/`strlcpy`) and compile with `-fstack-protector-strong`.
Spot the vulnerability: `buf[len] = '\0';` where `len` can equal `sizeof(buf)`	Off-by-one overflow: writing at index `sizeof(buf)` corrupts the adjacent byte — a stack canary or neighboring variable — without a full smash. Fix: ensure `len < sizeof(buf)`; reserve the last slot for the terminator.
Spot the vulnerability: writing past a `malloc`'d chunk into the next allocation	Heap overflow: it can corrupt allocator metadata or an adjacent object's fields, enabling a later control-flow hijack when that data is used. Fix: bound all heap writes to the allocated size; use hardened allocators and ASan in testing.
Spot the vulnerability: freeing an object, then later calling `obj->vtable->fn()` on it	Use-after-free control-flow hijack: the freed memory can be reallocated with attacker-controlled bytes, so the stale function pointer/vtable call jumps to their code. Fix: null the pointer after `free`, and never use an object after freeing it.
Spot the vulnerability: `free(p)` called twice due to two cleanup paths	Double-free for heap grooming: corrupting free-list structures can let an attacker make `malloc` return a chosen address. Fix: single ownership and a single free per object; set `p = NULL` after freeing.
Spot the vulnerability: `printf(user_input)` with `%x`/`%n` reachable	Format-string arbitrary read/write: `%x`/`%s` leak stack memory and `%n` writes an attacker-chosen value to an attacker-chosen address. Fix: `printf("%s", user_input)`; compile with `-Wformat -Wformat-security`.
Spot the vulnerability: `p = malloc(count * size);` then a loop writing `count` elements	Integer overflow → undersized allocation: the product wraps to a small value, so writing `count` elements overflows the heap — the pattern behind many CVEs. Fix: check `count > SIZE_MAX / size` (or use `calloc`) before allocating.
Spot the vulnerability: `memcpy(out, buf, client_len)` where `client_len` is client-supplied	Buffer over-read / disclosure (Heartbleed): if `client_len` exceeds the real data, the reply leaks adjacent memory (keys, other users' data). Fix: validate `client_len` against the actual received payload length.
Spot the vulnerability: sending a `struct` over the network without zeroing its padding	Uninitialized-memory disclosure: padding bytes and unset fields carry stale stack/heap data to the peer. Fix: `memset(&s, 0, sizeof s)` before filling, or serialize field-by-field rather than dumping raw bytes.
Spot the vulnerability: `return table[user_index];` with no bounds check	Out-of-bounds read from an untrusted index → memory disclosure or crash. Fix: validate `if (user_index >= 0 && (size_t)user_index < table_len)` before indexing (mind signedness).
Spot the vulnerability: reading a length field from the wire and `memcpy`ing that many bytes into a fixed buffer	Missing length validation: a malicious length overflows the destination. Fix: check the length against the buffer size (and against the bytes actually received) before copying.
Spot the vulnerability: `access(path, W_OK)` then later `open(path, O_WRONLY)`	TOCTOU race: the file can be swapped (e.g. via symlink) between the check and the open, so you write the wrong file with elevated rights. Fix: drop the `access` check and instead `open` with the right privileges/flags (`O_NOFOLLOW`), acting on the fd.
Spot the vulnerability: a setuid-root program that runs `system("...")` without dropping privileges	Privilege escalation: attacker-influenced code runs as root. Also risky is checking permissions with the real UID but acting with the effective UID. Fix: drop privileges (`setuid(getuid())`) before running external code, and avoid `system`.
Spot the vulnerability: `setuid(getuid());` with the return value ignored	Silent failure to drop privileges: if `setuid` fails, the "unprivileged" code that follows still runs as root. Fix: check the return value and abort on failure before doing anything else.
Spot the vulnerability: a setuid program that runs a helper relying on `$PATH`/`$IFS`/`$LD_PRELOAD`	Environment trust → injection: an attacker sets those variables to load or run malicious code as root. Fix: sanitize/reset the environment, use absolute paths, and drop privileges before exec.
Spot the vulnerability: building `"grep " + user + " file"` and passing it to `popen`	Command injection: metacharacters (`;`, `|`, `` ` ``, `$()`) in `user` run arbitrary commands. Fix: use `fork`+`exec*` with the user string as a separate argument (no shell), and validate the input.
Spot the vulnerability: `fopen(base_dir_concat(user_path), "r")` with `user_path` containing `../`	Path traversal: `../` escapes the intended directory, exposing arbitrary files. Fix: canonicalize with `realpath` and verify the result stays under the allowed base; reject `..` and absolute paths.
Spot the vulnerability: validating a filename string that an attacker embedded a `\0` into	Null-byte injection: the embedded `\0` truncates the C string at a different point than the validator expected, so a check on the visible suffix is bypassed. Fix: validate on the true length (reject embedded NULs), and don't mix length-bounded data with C-string APIs.
Spot the vulnerability: creating a temp file via a predictable `tmpnam` name	Insecure temp file: an attacker can pre-create or symlink the predictable path (a race). Fix: use `mkstemp`, which atomically creates and opens a uniquely-named file with safe permissions.
Spot the vulnerability: `int len = get_len(); if (len < MAX) memcpy(dst, src, len);`	Signed/unsigned bounds bypass: a negative `len` passes `len < MAX`, then converts to a huge `size_t` in `memcpy` — massive overflow. Fix: use an unsigned type and check both bounds: `if (len > 0 && (size_t)len < MAX)`.
Spot the vulnerability: session tokens from `srand(time(NULL)); id = rand();`	Predictable randomness: time-seeded `rand` is guessable, so tokens/keys/nonces can be forged. Fix: use a CSPRNG (`getrandom`, `/dev/urandom`, `arc4random`) for security-sensitive values.
Spot the vulnerability: a decryption key left in a heap buffer and `free`d without wiping, or a password compiled into the binary	Secrets in memory / hardcoded credentials: freed-but-unwiped secrets can leak via reuse/dumps, and embedded credentials are extractable with `strings`. Fix: wipe with `explicit_bzero` before `free`, and load credentials from secure external configuration.
Spot the vulnerability: `if (memcmp(input_mac, real_mac, len) == 0) accept();`	Timing side-channel: `memcmp` returns at the first mismatch, leaking how many leading bytes were correct — enabling byte-by-byte forgery. Fix: use a constant-time comparison that always inspects every byte.
