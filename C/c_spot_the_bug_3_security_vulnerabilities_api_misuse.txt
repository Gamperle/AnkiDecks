# 3.11 Security Vulnerabilities & Exploitation
Spot the vulnerability: unbounded `strcpy` of user input into a fixed stack buffer	Classic stack smashing: the overflow can overwrite the saved return address, redirecting execution (to shellcode or via ROP). Fix: bound the copy (`snprintf`/`strlcpy`) and compile with `-fstack-protector-strong`.
Spot the vulnerability: `buf[len] = '\0';` where `len` can equal `sizeof(buf)`	Off-by-one overflow: writing at index `sizeof(buf)` corrupts the adjacent byte — a stack canary or neighboring variable — without a full smash. Fix: ensure `len < sizeof(buf)`; reserve the last slot for the terminator.
Spot the vulnerability: writing past a `malloc`'d chunk into the next allocation	Heap overflow: it can corrupt allocator metadata or an adjacent object's fields, enabling a later control-flow hijack when that data is used. Fix: bound all heap writes to the allocated size; use hardened allocators and ASan in testing.
Spot the vulnerability: freeing an object, then later calling `obj->vtable->fn()` on it	Use-after-free control-flow hijack: the freed memory can be reallocated with attacker-controlled bytes, so the stale function pointer/vtable call jumps to their code. Fix: null the pointer after `free`, and never use an object after freeing it.
Spot the vulnerability: `free(p)` called twice due to two cleanup paths	Double-free for heap grooming: corrupting free-list structures can let an attacker make `malloc` return a chosen address. Fix: single ownership and a single free per object; set `p = NULL` after freeing.
Spot the vulnerability: `printf(user_input)` with `%x`/`%n` reachable	Format-string arbitrary read/write: `%x`/`%s` leak stack memory and `%n` writes an attacker-chosen value to an attacker-chosen address. Fix: `printf("%s", user_input)`; compile with `-Wformat -Wformat-security`.
Spot the vulnerability: `p = malloc(count * size);` then a loop writing `count` elements	Integer overflow → undersized allocation: the product wraps to a small value, so writing `count` elements overflows the heap — the pattern behind many CVEs. Fix: check `count > SIZE_MAX / size` (or use `calloc`) before allocating.
Spot the vulnerability: `memcpy(out, buf, client_len)` where `client_len` is client-supplied	Buffer over-read / disclosure (Heartbleed): if `client_len` exceeds the real data, the reply leaks adjacent memory (keys, other users' data). Fix: validate `client_len` against the actual received payload length.
Spot the vulnerability: sending a `struct` over the network without zeroing its padding	Uninitialized-memory disclosure: padding bytes and unset fields carry stale stack/heap data to the peer. Fix: `memset(&s, 0, sizeof s)` before filling, or serialize field-by-field rather than dumping raw bytes.
Spot the vulnerability: `return table[user_index];` with no bounds check	Out-of-bounds read from an untrusted index → memory disclosure or crash. Fix: validate `if (user_index >= 0 && (size_t)user_index < table_len)` before indexing (mind signedness).
Spot the vulnerability: reading a length field from the wire and `memcpy`ing that many bytes into a fixed buffer	Missing length validation: a malicious length overflows the destination. Fix: check the length against the buffer size (and against the bytes actually received) before copying.
Spot the vulnerability: `access(path, W_OK)` then later `open(path, O_WRONLY)`	TOCTOU race: the file can be swapped (e.g. via symlink) between the check and the open, so you write the wrong file with elevated rights. Fix: drop the `access` check and instead `open` with the right privileges/flags (`O_NOFOLLOW`), acting on the fd.
Spot the vulnerability: a setuid-root program that runs `system("...")` without dropping privileges	Privilege escalation: attacker-influenced code runs as root. Also risky is checking permissions with the real UID but acting with the effective UID. Fix: drop privileges (`setuid(getuid())`) before running external code, and avoid `system`.
Spot the vulnerability: `setuid(getuid());` with the return value ignored	Silent failure to drop privileges: if `setuid` fails, the "unprivileged" code that follows still runs as root. Fix: check the return value and abort on failure before doing anything else.
Spot the vulnerability: a setuid program that runs a helper relying on `$PATH`/`$IFS`/`$LD_PRELOAD`	Environment trust → injection: an attacker sets those variables to load or run malicious code as root. Fix: sanitize/reset the environment, use absolute paths, and drop privileges before exec.
Spot the vulnerability: building `"grep " + user + " file"` and passing it to `popen`	Command injection: metacharacters (`;`, `|`, `` ` ``, `$()`) in `user` run arbitrary commands. Fix: use `fork`+`exec*` with the user string as a separate argument (no shell), and validate the input.
Spot the vulnerability: `fopen(base_dir_concat(user_path), "r")` with `user_path` containing `../`	Path traversal: `../` escapes the intended directory, exposing arbitrary files. Fix: canonicalize with `realpath` and verify the result stays under the allowed base; reject `..` and absolute paths.
Spot the vulnerability: validating a filename string that an attacker embedded a `\0` into	Null-byte injection: the embedded `\0` truncates the C string at a different point than the validator expected, so a check on the visible suffix is bypassed. Fix: validate on the true length (reject embedded NULs), and don't mix length-bounded data with C-string APIs.
Spot the vulnerability: creating a temp file via a predictable `tmpnam` name	Insecure temp file: an attacker can pre-create or symlink the predictable path (a race). Fix: use `mkstemp`, which atomically creates and opens a uniquely-named file with safe permissions.
Spot the vulnerability: `int len = get_len(); if (len < MAX) memcpy(dst, src, len);`	Signed/unsigned bounds bypass: a negative `len` passes `len < MAX`, then converts to a huge `size_t` in `memcpy` — massive overflow. Fix: use an unsigned type and check both bounds: `if (len > 0 && (size_t)len < MAX)`.
Spot the vulnerability: session tokens from `srand(time(NULL)); id = rand();`	Predictable randomness: time-seeded `rand` is guessable, so tokens/keys/nonces can be forged. Fix: use a CSPRNG (`getrandom`, `/dev/urandom`, `arc4random`) for security-sensitive values.
Spot the vulnerability: a decryption key left in a heap buffer and `free`d without wiping, or a password compiled into the binary	Secrets in memory / hardcoded credentials: freed-but-unwiped secrets can leak via reuse/dumps, and embedded credentials are extractable with `strings`. Fix: wipe with `explicit_bzero` before `free`, and load credentials from secure external configuration.
Spot the vulnerability: `if (memcmp(input_mac, real_mac, len) == 0) accept();`	Timing side-channel: `memcmp` returns at the first mismatch, leaking how many leading bytes were correct — enabling byte-by-byte forgery. Fix: use a constant-time comparison that always inspects every byte.


# 3.12 Initialization Order & VLA Bugs
Spot the bug: global in TU A's initializer reads a global defined in TU B	Undefined initialization order across translation units: C only guarantees statics are zero-initialized before dynamic initialization begins, but the order of dynamic initializers across TUs is unspecified. TU B's value may still be zero when TU A reads it. Fix: use lazy initialization inside a function.
Spot the bug: int arr[get_size()]; inside a function where get_size() could return 0 or a large value	VLA with unchecked size: a return value of 0 or negative is UB; a very large value silently overflows the stack with no failure indication (unlike malloc). Fix: validate the size is in a safe range before declaring the VLA, or use malloc for dynamic sizes.
Spot the bug: struct Msg m = {.type = 1}; send(fd, &m, sizeof m, 0);	Padding bytes disclosure: designated initializers zero named members but leave struct padding bytes at unspecified (stale stack) values. Sending sizeof(m) bytes leaks those bytes to the receiver. Fix: memset(&m, 0, sizeof m) before setting fields.
Spot the bug: static int counter = 0; inside a recursive function	Static local shared across recursive calls: the single instance accumulates state across all recursive levels — almost always unintended. Fix: use an automatic local variable or pass the counter as a parameter.
Spot the bug: malloc(0) result used as a valid buffer	Implementation-defined zero allocation: malloc(0) may return NULL or a unique non-dereferenceable non-NULL pointer. Dereferencing or writing through it is UB. Fix: treat zero-length allocations as a special case or allocate a minimum of 1 byte.


# 3.13 Linkage & Declaration Bugs
Spot the bug: calling result = compute(val); before any prototype for compute in C89 mode	Implicit function declaration: the compiler assumes int compute() accepting any arguments. If the real return type is a pointer or arguments differ, the call is UB (wrong value from wrong register/stack). Fix: always prototype functions before use; in C99+ this is a constraint violation.
Spot the bug: header declares extern int count; but the definition is long count = 0;	Mismatched extern declaration vs definition type: int and long differ in size on LP64 platforms. Reads through the int-typed reference read the wrong number of bytes. Fix: make declaration and definition use the identical type.
Spot the bug: both util.c and helpers.c define void log_msg(const char *s) { ... } with no static	Multiple definitions with external linkage (ODR violation): the linker may silently pick one or error out. Fix: add static to limit the definition to its own TU, or define it once and declare extern in a shared header.
Spot the bug: static int initialized = 0; in a header included by three .c files	Static variable in a header: each TU gets its own private copy. The flag is not shared across modules — each TU has its own version, so cross-module state never synchronizes. Fix: declare extern in the header and define once in a .c file.
Spot the bug: a C library header included from C++ without an extern "C" block	Missing extern "C" wrapper: C++ mangles function names, so the linker looks for _Z5funcv instead of func. The C object has func and the link fails or calls the wrong symbol. Fix: wrap the C header in #ifdef __cplusplus extern "C" { #endif ... #ifdef __cplusplus } #endif.


# 3.14 Struct / Union Misuse
Spot the bug: u.i = 42; float f = u.f; for a union { int i; float f; } u;	Reading an inactive union member: only the last-written member has a defined value in standard C. Reading u.f after writing u.i is a strict-aliasing violation. The safe portable way to type-pun is via memcpy or through unsigned char *. Many compilers support union type-punning as an extension, but it is not portable ISO C.
Spot the bug: assuming __attribute__((packed)) struct layout matches MSVC #pragma pack(1)	Packed struct portability: GCC and MSVC have different behaviors for nested structs, unions, and bitfields even when both "pack to 1 byte". Always verify layout with offsetof/sizeof assertions in a test, especially for protocol buffers shared across toolchains.
Spot the bug: struct Buf { int n; char data[]; } b; b.data[0] = 'x';	Flexible array member as a local variable: sizeof(struct Buf) equals sizeof(int) — data has no storage. Any write to b.data[i] is out-of-bounds. Flexible array members only work in heap-allocated structs: struct Buf *p = malloc(sizeof *p + N);.
Spot the bug: if (s1 == s2) where s1 and s2 are struct Point	Struct equality with == is a compile error in C (no operator overloading). Fix: compare field-by-field, or use memcmp(&s1, &s2, sizeof s1) only when you are certain there is no padding and no pointer members.
Spot the bug: Widget *copy = malloc(sizeof *copy); *copy = *original; then widget_destroy(original); then using copy	Shallow copy / use-after-free: *copy = *original copies pointer members by value. Both structs share the same heap data. Destroying original frees that data; copy's pointer members now dangle. Fix: perform a deep copy that duplicates all owned resources.


# 3.15 const & volatile Misuse
Spot the bug: two threads share volatile int flag; and both increment it without locking	volatile does not provide atomicity: flag++ is three operations (load, add, store) — none atomic. Two threads can read the same value, both add 1, and write back the same result. Fix: use _Atomic int flag or protect with a mutex.
Spot the bug: void process(const char *buf) — programmer assumes callers cannot modify buf	Misunderstanding const on a pointer parameter: const char *buf promises only that process will not write through buf — it says nothing about other aliases. const is a compile-time contract on this one function, not deep immutability of the data.
Spot the bug: char *p = (char *)read_only_str; p[0] = 'X';	Casting away const and writing: if read_only_str is a string literal or a const-qualified object in read-only memory, the write is UB and commonly causes a segfault. Only cast away const when you have external proof the underlying object is mutable.
Spot the bug: while (!done) {} where done is a plain int set to 1 in a signal handler	Missing volatile on a polling flag: the optimizer may hoist the load before the loop and test it once, producing an infinite loop even after the handler fires. Fix: declare volatile sig_atomic_t done = 0;.
Spot the bug: volatile int x shared between two threads used as the only synchronization	volatile prevents compiler caching but does not insert CPU memory fences. On multi-core hardware, a write on one core may not be visible to another due to store buffers. Fix: use _Atomic int x or a mutex for cross-thread communication.


# 3.16 API Contract Bugs
Spot the bug: size_t n = strlen(buf); where buf was filled by read() but not null-terminated	Non-null-terminated buffer to strlen: strlen scans until \0; if none exists within bounds it reads past the end — UB, possible crash or garbage. Fix: null-terminate explicitly after the read: buf[bytes_read] = '\0'; (ensure the buffer has at least one spare byte).
Spot the bug: char *val = getenv("PATH"); free(val);	Freeing getenv's return: getenv returns a pointer into the process environment block, not a malloc'd copy. Freeing it corrupts the environment. If you need a modifiable copy, use strdup(getenv("PATH")).
Spot the bug: char *msg = strerror(errno); /* long computation */ puts(msg);	Stale strerror result: the standard permits strerror to use a static buffer overwritten by the next call. A library call inside the computation block can clobber it. Fix: copy the message immediately with strerror_r or snprintf.
Spot the bug: void my_log(const char *fmt, ...) { printf(fmt, ...); }	Re-calling printf instead of forwarding va_list: the ... in my_log is its own argument pack; you cannot pass it directly to printf. Fix: va_start(ap, fmt); vprintf(fmt, ap); va_end(ap);.
Spot the bug: va_end(ap); return va_arg(ap, int);	Using va_arg after va_end: the va_list is in an indeterminate state after va_end. Any further va_arg call is UB. Always call va_end only after all arguments are consumed.
Spot the bug: outer strtok loop calls a function that also uses strtok on a different string	strtok maintains a hidden static pointer to the string being tokenized. The inner call clobbers it, causing the outer loop to lose its position. Fix: use strtok_r(str, delim, &saveptr) for both loops with separate saveptr variables.
