# Predict-the-output riddles on operator precedence traps, sequence points, and macro expansion pitfalls.

# 1. Precedence Traps
What does this print? `printf("%d", 5 & 3 == 3);`	`1` — `==` binds *tighter* than `&`, so this parses as `5 & (3 == 3)` = `5 & 1` = `1` (0b101 & 0b001), not the probably-intended `(5 & 3) == 3` (which would be `1 == 3` = `0`). Bitwise operators binding looser than comparison operators is one of C's most notorious gotchas — always parenthesize when mixing them.
What does this print? `int x = 1, y = 2; printf("%d", (x, y));`	`2` — the comma *operator* evaluates its left operand for side effects, discards its value, and yields the right operand. This is distinct from a comma used as an argument/declarator *separator*, which doesn't sequence or discard anything.
What does this print? `printf("%f", 1 ? 1 : 2.0);`	`1.000000` — the conditional operator's result type is the common type of *both* branches after the usual arithmetic conversions (`int` and `double` → `double`), regardless of which branch is actually selected. So even though the taken branch is the literal `int` `1`, the expression's type is `double`, and it evaluates to `1.0`. (Printing it with `%d` instead would be a format mismatch and undefined behavior, per the earlier riddles in this deck.)
What does this print? `int a = 5; if (a = 0) printf("true"); else printf("false: a=%d", a);`	`false: a=0` — `=` is assignment, not comparison. `a = 0` assigns 0 to `a` and the whole expression evaluates to 0 (falsy), so the `else` branch runs, and `a` has now been clobbered to 0 as a side effect. The intended `a == 0` was probably meant. Writing "Yoda conditions" (`0 == a`) turns this typo into a compile error instead of a silent bug.
What does this print? `printf("%d", !!5);`	`1` — `!5` is `0` (since 5 is nonzero/truthy, its logical negation is false), and `!0` is `1`. Double-negation is a common (if slightly obscure) idiom for normalizing any nonzero value down to exactly `1`.

# 2. Sequencing (Undefined in C — Contrast with Java!)
What does this print? `int i = 1; int r = i++ + i++; printf("%d %d", r, i);`	Undefined behavior — both `i++` operations modify the same object `i` with no sequence point between them, so the standard imposes no order and no defined result. This is genuinely different from Java, where `i++ + i++` for `i=1` is fully specified (left operand evaluated fully before the right) and always gives the same deterministic answer on every JVM.
What does this print? `int a[3] = {0}; int i = 0; a[i] = i++;`	Undefined behavior — whether the array index `i` on the left side is read before or after the increment on the right side is unsequenced, so which element gets written (and what value) is not defined by the standard, and different compilers/optimization levels may disagree.
What happens here? `int x = 0; if (x != 0 && 10 / x > 1) { ... }`	No division-by-zero occurs — `&&` short-circuits: because `x != 0` is false, the right operand `10 / x` is never evaluated at all. This short-circuit guarantee (unlike plain `&`) is exactly why guard patterns like `if (p != NULL && p->field)` are safe.

# 3. Macro Pitfalls
What does this print? `#define SQUARE(x) x*x` then `printf("%d", SQUARE(1+2));`	`5`, not `9` — naive textual substitution expands this to `1+2*1+2`, and with normal precedence (`*` before `+`) that's `1 + 2 + 2 = 5`. The fix is to parenthesize both the parameter and the whole macro body: `#define SQUARE(x) ((x)*(x))`.
What does this print? `#define MAX(a,b) ((a)>(b)?(a):(b)) int i=5, j=3; printf("%d %d", MAX(i++, j++), i);`	Undefined/surprising: because `a` (i.e. `i++`) appears twice in the expansion `((i++)>(j++)?(i++):(j++))`, and `i > j` is true here, `i++` gets evaluated *twice* — once for the comparison, once again for the "then" branch — incrementing `i` twice instead of once, alongside multiple unsequenced side effects on `i`. Macros that evaluate an argument more than once are a classic source of double-evaluation bugs; a real function argument is only ever evaluated once.
What does this print? `#define N 5+1 printf("%d", 10 * N);`	`51`, not `60` — the macro body `5+1` is substituted verbatim with no surrounding parentheses, so `10 * N` becomes `10 * 5 + 1` = `51`. Always wrap macro replacement text in parentheses: `#define N (5+1)`.
