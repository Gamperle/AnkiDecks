# Predict-the-output riddles on pointer arithmetic, array decay, and pointer/array equivalence quirks.

# 1. sizeof, Decay & Arithmetic
What does this print? `int arr[5]; printf("%zu", sizeof(arr));` (in the same scope as the declaration)	`20` — inside the scope where it's declared, `arr` is a genuine array of 5 `int`s, so `sizeof` reports the whole array's byte size (5 × 4).
What does this print? `void f(int arr[5]) { printf("%zu", sizeof(arr)); } int main(){ int a[5]={0}; f(a); }`	`8` on a 64-bit platform (or `4` on 32-bit) — not `20`. Once `arr` is a function parameter, it's really just `int *arr`: arrays always decay to a pointer when passed to a function. So `sizeof(arr)` inside `f` measures the *pointer*, and the original "5" is gone without a trace.
What does this print? `int a[3] = {1,2,3}; int *p = a; printf("%d", *(p+1));`	`2` — pointer arithmetic is automatically scaled by the size of what's pointed to. `p + 1` moves forward by one `int`, not one byte, landing on `a[1]`.
Does this compile, and what does it print? `int a[5] = {10,20,30,40,50}; printf("%d", 2[a]);`	Compiles, and prints `30`. `a[i]` is just shorthand for `*(a + i)`, and addition doesn't care about operand order — so `2[a]` means exactly the same thing as `a[2]`. It's legal C, but nobody should actually write it this way.
What does this print? `int a[2][3] = {{1,2,3},{4,5,6}}; printf("%d", a[1][0] - a[0][0]);`	`3` — 2D arrays are stored row by row, contiguously. `a[1][0]` sits exactly one full row (3 `int`s) after `a[0][0]` in memory, and that's exactly the distance the subtraction reports.
What does this print? `void mod(int a[]) { a[0] = 99; } int main(){ int arr[3]={1,2,3}; mod(arr); printf("%d", arr[0]); }`	`99` — C is often called strictly "pass by value," and it is, but for an array the *value* being passed is a pointer, and that pointer still points at the caller's real data. A write through it is visible back in `main`. There's no way to pass a whole array by value in C, only the pointer that stands in for it.

# 2. Lifetime & Undefined Behavior
What happens here? `char *s = "hello"; s[0] = 'H'; printf("%s", s);`	Undefined behavior. String literals typically live in read-only memory, so writing through `s` often crashes immediately — though the standard doesn't require a crash, it just doesn't let you rely on anything. Use `const char *` for a literal, and copy it into a real `char[]` if you need a mutable version.
What happens here? `int *p; { int x = 5; p = &x; } printf("%d", *p);`	Undefined behavior. `x` only exists inside its own `{ }` block; once that block ends, `p` points at memory that's no longer reserved for anything. Dereferencing it might print `5` by luck (nothing has overwritten that stack slot yet), or it might crash, or print garbage — nothing is guaranteed either way.
What happens here? `int *f(void) { int x = 42; return &x; }` then the caller dereferences the returned pointer.	Undefined behavior, for the same reason as above: `x` disappears the moment `f` returns, leaving the caller holding a dangling pointer. Most compilers warn about exactly this pattern ("returning address of local variable") — never ignore that warning.
What happens here? `int a[3] = {1,2,3}; int *p = a + 3; printf("%d", *p);`	Undefined behavior — but notice where the line actually is. Computing `a + 3` (one past the last element) is explicitly allowed by the standard, and you can safely compare it to other pointers. What's *not* allowed is dereferencing it: `a[3]` doesn't exist, so reading `*p` is UB even though computing `p` itself was completely fine.
What happens here? `char *p = NULL; p += 5; printf("%p", (void*)p);`	Undefined behavior. Pointer arithmetic is only meaningful relative to an actual array, and a null pointer isn't pointing into any array at all. Most implementations will happily print something like "address 5" without complaint, but the standard doesn't promise that, or anything else.
What happens here? `int a, b; int *p = &a, *q = &b; if (p < q) printf("less");`	Undefined behavior, even though it will almost always just print `0` or `1` without complaint. Ordering comparisons (`<`, `>`) are only well-defined between pointers into the *same* array — `p` and `q` point at two separate variables, so the standard places no constraints on the result. Only equality (`==`/`!=`) is safe to use between pointers to unrelated objects.
