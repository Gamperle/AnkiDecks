# 1. Signed vs Unsigned
What does this print (on a typical two's-complement system)? `int x = INT_MAX; x++; printf("%d", x);`	Undefined behavior. In practice, with most compilers at low optimization, `x` wraps to `INT_MIN`. But signed overflow is UB in C, not guaranteed wraparound — an optimizing compiler is legally allowed to assume it never happens, and may eliminate code that depends on it (e.g. an overflow check written as `if (x+1 < x)`).
What does this print? `unsigned int x = 0; x--; printf("%u", x);`	`4294967295` (i.e. `UINT_MAX` on a 32-bit `unsigned int`) — unlike signed overflow, unsigned arithmetic is fully defined to wrap modulo 2^N, so this is not UB, just modular arithmetic.
What does this print? `printf("%d", -1 < 0u);`	`0` (false) — mixing a signed and unsigned operand in a comparison triggers the "usual arithmetic conversions": the `int -1` is converted to `unsigned int`, becoming `UINT_MAX`, which is certainly not less than `0u`. This is a classic source of silently-bypassed bounds checks.
What does this print (assuming plain `char` is signed, the common case on x86/ARM Linux)? `char c = 200; printf("%d", c);`	`-56` — 200 is outside signed `char`'s range (-128..127 typically), so storing it is implementation-defined; on the vast majority of real compilers/platforms it wraps by reinterpreting the bit pattern, giving 200-256 = -56. On a platform where plain `char` is unsigned, this would print `200` instead.
What does this print? `size_t n = sizeof(int) - 10; printf("%zu", n);`	A huge number near `SIZE_MAX` (e.g. `18446744073709551610` on a 64-bit `size_t`), not `-6`. `sizeof` yields an *unsigned* `size_t`, so `4 - 10` never goes negative — it wraps modulo 2^64 just like any unsigned subtraction.
What does this print? `int a = 5, b = 2; printf("%f", a / b);`	Undefined behavior with garbage-looking output — `a / b` is ordinary `int` division (`2`), but `%f` expects a `double` argument. Passing an `int` where `printf` expects `double` is a format/argument type mismatch, which is UB in C: the value printed will be nonsense bits reinterpreted as a double, not `2.000000`.
Does this compile and what does it print? `unsigned char uc = 255; uc++; printf("%d", uc);`	Compiles fine, prints `0` — `unsigned char` wraps modulo 256, fully defined behavior (unlike the signed `char` case above, unsigned types never have implementation-defined or undefined overflow).
What does this print (typical two's-complement, `int`-promotion platform)? `short s = 32767; s++; printf("%d", s);`	Typically `-32768` — `s` is promoted to `int` for the addition (`32767+1=32768`, which fits fine in `int`), but assigning that `int` back into the narrower `short` is a conversion of an out-of-range value to a signed type, which the standard leaves implementation-defined. Virtually every real compiler truncates the bit pattern, giving -32768, but it is not a portability guarantee.
What does this print (assuming a signed 8-bit `char`)? `char a = 100, b = 100; char c = a + b; printf("%d", c);`	Typically `-56` — `a + b` is computed in promoted `int` (200, no overflow there), but storing 200 back into a `char` is out-of-range for signed `char` (-128..127) and is implementation-defined, commonly wrapping to 200-256=-56.

# 2. Undefined Shifts & Division
What does this print? `int x = 1; printf("%d", x << 32);`	Undefined behavior — the shift amount must be strictly less than the width of the (promoted) left operand's type; shifting a 32-bit `int` by 32 or more is UB, not "shifts to zero" as some might guess.
What does this print? `int x = -1; printf("%d", x << 1);`	Undefined behavior — left-shifting a *negative* value is UB in C (in every standard revision through C17), regardless of what a particular compiler happens to output. Do bit-shifting on unsigned types if you need well-defined semantics.
What does this print? `printf("%d %d", -7 / 2, -7 % 2);`	`-3 -1` — since C99, integer division truncates toward zero (not toward negative infinity), so -7/2 is -3 (not -4); and because `(a/b)*b + a%b == a` must hold, the remainder is -1.
What happens here? `int i = -1; size_t len = 5; if (i < len) { /* assume in-bounds */ }`	The branch is never taken, "surprisingly" — comparing a signed `int` against an unsigned `size_t` converts `i` to unsigned, turning -1 into a huge value, so `i < len` is false even though -1 is obviously less than 5 mathematically. This exact pattern is a real-world source of bypassed bounds checks in security-sensitive code.
