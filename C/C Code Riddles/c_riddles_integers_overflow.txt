# Predict-the-output riddles on signed/unsigned behavior, integer promotion, and overflow. Note where the standard says "undefined" vs "implementation-defined" vs actually-guaranteed.

# 1. Signed vs Unsigned
What does this print (on a typical two's-complement system)? `int x = INT_MAX; x++; printf("%d", x);`	Undefined behavior — not a guaranteed wraparound. On most real compilers, at low optimization, `x` does wrap to `INT_MIN`. But the standard permits anything here, and optimizing compilers actively exploit this: they're allowed to assume signed overflow never happens, and may delete code that checks for it (like `if (x + 1 < x)`).
What does this print? `unsigned int x = 0; x--; printf("%u", x);`	`4294967295` (`UINT_MAX` for a 32-bit `unsigned int`). Unlike signed overflow, unsigned arithmetic is fully defined: it always wraps modulo 2^N. This is normal, guaranteed behavior, not undefined behavior.
What does this print? `printf("%d", -1 < 0u);`	`0` (false) — surprising, since -1 is obviously less than 0. When a signed value is compared against an unsigned one, C silently converts the signed value to unsigned first. So `-1` becomes `UINT_MAX`, and `UINT_MAX < 0u` is false. This silent conversion is a classic way bounds checks get bypassed.
What does this print (assuming plain `char` is signed, the common case on x86/ARM Linux)? `char c = 200; printf("%d", c);`	`-56` on most platforms. `200` doesn't fit in a signed `char` (roughly -128..127), so the standard leaves the result up to the implementation. Nearly every real compiler just reinterprets the bit pattern, giving 200 − 256 = −56. On a platform where plain `char` is unsigned, this would print `200` instead.
What does this print? `size_t n = sizeof(int) - 10; printf("%zu", n);`	A huge number, not `-6`. `sizeof` returns an *unsigned* `size_t`, so `4 - 10` can't go negative — it wraps around to a value near `SIZE_MAX`, the same way any unsigned subtraction underflows.
What does this print? `int a = 5, b = 2; printf("%f", a / b);`	Undefined behavior, and probably not `2.000000`. `a / b` is ordinary integer division, giving `2` — but `%f` tells `printf` to expect a `double`. Passing an `int` where a `double` is expected is a type mismatch that `printf` has no way to catch at compile time, so the raw bits of the `int` get reinterpreted as part of a `double`, producing garbage.
Does this compile, and what does it print? `unsigned char uc = 255; uc++; printf("%d", uc);`	Compiles fine, prints `0`. `unsigned char` just wraps modulo 256 — this is defined behavior, not UB: unsigned types always wrap on overflow, no matter their width.
What does this print (typical two's-complement platform)? `short s = 32767; s++; printf("%d", s);`	Typically `-32768`, but not guaranteed. `s` is first promoted to `int` to do the addition (32767+1 = 32768, which fits fine in `int`). The problem comes when that 32768 has to be squeezed back into a 16-bit `short` — since it doesn't fit, the standard leaves the result implementation-defined. Virtually every real compiler just truncates the bits, giving -32768, but that's not something you can portably rely on.
What does this print (assuming a signed 8-bit `char`)? `char a = 100, b = 100; char c = a + b; printf("%d", c);`	Typically `-56` — the same idea as the `short` example above, just at 8 bits instead of 16. `a + b` is computed as `int` (200, no problem there), but storing 200 back into a signed `char` (range -128..127) is out of range, so the result is implementation-defined — in practice, a truncated `-56`.

# 2. Undefined Shifts & Division
What does this print? `int x = 1; printf("%d", x << 32);`	Undefined behavior — not `0` as you might guess. A shift amount must be strictly less than the bit-width of the type being shifted; shifting a 32-bit `int` by 32 or more simply isn't allowed, and the compiler is free to produce anything at all, including different results on different builds.
What does this print? `int x = -1; printf("%d", x << 1);`	Undefined behavior. Left-shifting a *negative* value is undefined in every version of C through C17, no matter what a specific compiler happens to output. If you need well-defined shift behavior, shift an unsigned type instead.
What does this print? `printf("%d %d", -7 / 2, -7 % 2);`	`-3 -1`. Since C99, integer division truncates toward zero, so `-7 / 2` rounds toward `0`, giving `-3` (not `-4`). The remainder then has to satisfy `(a/b)*b + a%b == a`, which forces `-7 % 2` to be `-1`.
What happens here? `int i = -1; size_t len = 5; if (i < len) { /* assume in-bounds */ }`	The branch never runs — the surprising part. Comparing a signed `int` against an unsigned `size_t` converts `i` to unsigned first, turning `-1` into a huge number, so `i < len` is false even though -1 is obviously less than 5. This exact pattern has bypassed real bounds checks in real security bugs.
