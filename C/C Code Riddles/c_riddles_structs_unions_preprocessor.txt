# 1. Struct Layout
What does this print (typical 64-bit platform, default alignment)? `struct S { char c; int i; }; printf("%zu", sizeof(struct S));`	`8`, not `5` — `int` needs 4-byte alignment, so the compiler inserts 3 padding bytes after `c` to align `i`, giving 1 + 3 + 4 = 8. Exact padding is implementation-defined, but "sum of the members' sizes" is essentially never the real answer once alignment differs between fields.
What does this print? `struct A { char a; char b; int i; }; struct B { char a; int i; char b; }; printf("%zu %zu", sizeof(struct A), sizeof(struct B));`	`8 12` — `A` packs both `char`s together before the 4-byte-aligned `int` (1+1+2 padding+4=8), while `B` interleaves them, forcing padding after `a` *and* after `b` (1+3+4+1+3=12). Reordering struct members from largest-to-smallest alignment is a common technique to shrink structs with no functional change.
What does this print? `struct S { int len; int data[]; }; printf("%zu", sizeof(struct S));`	`4` (just `sizeof(int)`) — `data` is a C99 flexible array member; it contributes *zero* to `sizeof(struct S)` by definition. The actual storage for `data` is provided by over-allocating the struct at `malloc` time, e.g. `malloc(sizeof(struct S) + n * sizeof(int))`.

# 2. Unions & Type Punning
What does this print (IEEE-754 `float`, 32-bit `int`)? `union U { int i; float f; } u; u.f = 1.0f; printf("%d", u.i);`	`1065353216` — not `1`! Reading `u.i` after writing `u.f` reinterprets the *raw bit pattern* of the `float` (0x3F800000 for 1.0f) as an `int`, which is a completely different number from the mathematical value 1. A `union` is the one standard-sanctioned way to type-pun in C (reading a different member than you last wrote is explicitly allowed for unions) — doing the equivalent via a pointer cast (`*(int*)&f`) is a strict-aliasing violation and UB instead.
Is the memory layout (bit order/packing) of this guaranteed to be portable? `struct Flags { unsigned a : 1; unsigned b : 1; unsigned c : 1; };`	No — the C standard leaves bit-field allocation order, packing, and whether a field can straddle a storage-unit boundary entirely implementation-defined. Code that relies on a specific bit-field layout (e.g. to match a hardware register or a wire protocol) is inherently non-portable across compilers/platforms.

# 3. Enums & the Preprocessor
What are the values of `RED`, `GREEN`, `BLUE`? `enum Color { RED, GREEN = 5, BLUE };`	`RED=0`, `GREEN=5`, `BLUE=6` — an unspecified enumerator defaults to one more than the *previous* enumerator's value (starting at 0 for the first); explicitly assigning `GREEN=5` doesn't affect `RED` (already fixed at 0) but resets the auto-increment baseline for everything after it, so `BLUE` becomes 6, not 2.
What does this expand to, and what does it print? `#define CONCAT(a,b) a##b int foobar = 42; printf("%d", CONCAT(foo,bar));`	`42` — the `##` token-pasting operator glues the two argument tokens into a single new token *before* the rest of the compiler sees them, so `CONCAT(foo,bar)` literally becomes the identifier `foobar`, which then resolves to the existing variable.
What does this print? `#define STR(x) #x printf("%s", STR(1+2));`	`1+2` (the literal four-character string `"1+2"`) — the `#` stringizing operator turns a macro argument into a string literal of its *unexpanded source text*, verbatim, rather than evaluating it as an expression first.
Does this cause infinite macro expansion? `#define X X + 1 int y = X;`	No — the C preprocessor specifically prevents a macro from expanding itself recursively (informally called "blue paint" / "painted blue"): while `X` is in the middle of being replaced, any further occurrence of `X` inside its own replacement text is left untouched. So `X` expands exactly once, to the literal text `X + 1`, and stops.
