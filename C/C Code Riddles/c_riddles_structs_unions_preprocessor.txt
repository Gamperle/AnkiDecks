# Predict-the-output riddles on struct padding, union type punning, enums, bit-fields, and macro mechanics.

# 1. Struct Layout
What does this print (typical 64-bit platform, default alignment)? `struct S { char c; int i; }; printf("%zu", sizeof(struct S));`	`8`, not `5`. An `int` needs to start at a 4-byte-aligned address, so the compiler inserts 3 padding bytes after `c` to push `i` into position: 1 + 3 + 4 = 8. The exact padding isn't standardized, but on any typical platform "sum of the member sizes" is essentially never the real answer once alignment differs between fields.
What does this print? `struct A { char a; char b; int i; }; struct B { char a; int i; char b; }; printf("%zu %zu", sizeof(struct A), sizeof(struct B));`	`8 12` — same fields, different order, different size. `A` groups its two `char`s together before the 4-byte-aligned `int` (1+1+2 padding+4 = 8). `B` puts a `char` on each side of the `int`, forcing padding twice (1+3+4+1+3 = 12). Ordering struct members from largest alignment to smallest is a free way to shrink a struct.
What does this print? `struct S { int len; int data[]; }; printf("%zu", sizeof(struct S));`	`4` (just `sizeof(int)`) — a C99 flexible array member contributes *nothing* to `sizeof`. The real storage for `data` comes from deliberately over-allocating the struct: `malloc(sizeof(struct S) + n * sizeof(int))`.

# 2. Unions & Type Punning
What does this print (IEEE-754 `float`, 32-bit `int`)? `union U { int i; float f; } u; u.f = 1.0f; printf("%d", u.i);`	`1065353216`, not `1`. Writing `u.f` and reading `u.i` reinterprets the exact same bits, but as a totally different kind of number: what prints is the raw IEEE-754 bit pattern of the float `1.0`, read as if it were a plain integer. A `union` is the one place C explicitly allows this kind of byte-level reinterpretation (reading back a different member than you last wrote) — doing the same thing through a pointer cast (`*(int*)&f`) is undefined behavior instead.
Is the memory layout (bit order/packing) of this guaranteed to be portable? `struct Flags { unsigned a : 1; unsigned b : 1; unsigned c : 1; };`	No — the standard deliberately leaves bit-field order and packing up to the compiler. Two different compilers, or even the same compiler on two platforms, are allowed to lay these bits out completely differently. Never rely on a specific bit-field layout for anything that has to match a fixed format, like a hardware register or a wire protocol.

# 3. Enums & the Preprocessor
What are the values of `RED`, `GREEN`, `BLUE`? `enum Color { RED, GREEN = 5, BLUE };`	`RED=0`, `GREEN=5`, `BLUE=6`. Each enumerator defaults to one more than the previous one (starting at 0 for the very first). Explicitly setting `GREEN=5` doesn't touch `RED` (already fixed at 0), but it does reset the counter going forward — so `BLUE`, coming right after, becomes 6.
What does this expand to, and what does it print? `#define CONCAT(a,b) a##b int foobar = 42; printf("%d", CONCAT(foo,bar));`	`42` — the `##` operator glues its two arguments into one token *before* the compiler ever sees them as separate things. So `CONCAT(foo,bar)` doesn't produce `foo` followed by `bar`; it produces the single identifier `foobar`, which the compiler then resolves to the existing variable of that name.
What does this print? `#define STR(x) #x printf("%s", STR(1+2));`	`1+2` (the four-character string literal `"1+2"`). The `#` operator turns whatever text you pass in into a string, exactly as written, without evaluating it as an expression first.
Does this cause infinite macro expansion? `#define X X + 1 int y = X;`	No. The preprocessor has a built-in guard against a macro expanding itself: while `X` is being replaced, any `X` that shows up *inside* that replacement is left alone rather than expanded again. So `X` turns into `X + 1` exactly once, and stops there.
