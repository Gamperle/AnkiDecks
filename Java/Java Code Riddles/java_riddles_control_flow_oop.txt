# Predict-the-output riddles on static vs dynamic dispatch, finally semantics, overload resolution, and other OOP surprises.

# 1. finally vs return
What does this print? `static int f() { try { return 1; } finally { return 2; } } System.out.println(f());`	`2` — a `return` inside `finally` unconditionally overrides any `return` (or thrown exception) from the `try` block. Most linters flag this as a code smell precisely because it's so surprising.
What does this print? `static int f() { try { throw new RuntimeException("boom"); } finally { return 1; } } System.out.println(f());`	`1` — and the `RuntimeException` is silently discarded! A `return` in `finally` doesn't just override a normal return value, it swallows an in-flight exception entirely, with no trace of it anywhere. This is one of the strongest arguments for never putting `return` inside `finally`.
What does this print? `try (AutoCloseable c = () -> { throw new RuntimeException("close-fail"); }) { throw new RuntimeException("body-fail"); } catch (Exception e) { System.out.println(e.getMessage() + " / " + e.getSuppressed().length); }`	`body-fail / 1` — try-with-resources behaves oppositely from a manual `finally`: if both the body and the automatic `close()` throw, the *body's* exception is the one that propagates, and the `close()` exception is attached as a suppressed exception (retrievable via `getSuppressed()`), not lost and not overriding.

# 2. Static Dispatch vs Dynamic Dispatch
What does this print? `class A { static String who(){return "A";} } class B extends A { static String who(){return "B";} } A a = new B(); System.out.println(a.who());`	`A` — static methods are **hidden**, not overridden, and are never polymorphic: a call through a reference is resolved at compile time using the reference's *declared* type, ignoring the actual runtime object. Calling a static method "through an instance" is legal but misleading syntax sugar.
What does this print? `class A { int x = 1; } class B extends A { int x = 2; } A a = new B(); System.out.println(a.x);`	`1` — fields are also resolved statically by declared type, not dynamically like methods. `B`'s field `x` *hides* `A`'s field of the same name rather than overriding it; accessing `a.x` through an `A`-typed reference always sees `A`'s field, even though `a` is really a `B` at runtime.
What does this print? `class A { A(){ init(); } void init(){ System.out.println("A.init"); } } class B extends A { int x = 10; void init(){ System.out.println("x=" + x); } } new B();`	`x=0` — the superclass constructor runs *before* the subclass's field initializers, but it calls the overridden (dynamically dispatched) `init()`. At that point `B.init()` executes and reads `x`, which hasn't been assigned 10 yet — it's still the default `0`. Calling overridable methods from a constructor is a classic trap.
What does this print? `Object[] arr = new String[3]; arr[0] = 42; System.out.println("reached");` (assume it compiles)	It never reaches the println — this throws `ArrayStoreException` at runtime. Arrays are *covariant* in Java (`String[]` is-a `Object[]`), so the assignment to the `Object[]`-typed variable compiles fine, but every array carries its actual runtime element type, and the JVM checks each store against it — storing an `Integer` into what's really a `String[]` fails at the point of the write.

# 3. Overload Resolution
What gets called? `void f(long x){ System.out.println("long"); } void f(Integer x){ System.out.println("Integer"); } f(5);`	`"long"` — Java's overload resolution tries phases in strict order: (1) exact match / widening primitive conversion, (2) boxing/unboxing, (3) varargs. A widening `int → long` conversion is found in phase 1, before boxing `int → Integer` is even considered in phase 2 — even though `Integer` "feels" closer to `int`.
What gets called? `void f(int x){} void f(Integer x){} f(5);`	`f(int)` — an exact primitive match always wins over one requiring a boxing conversion.
Does this compile? `interface A { default String greet(){return "A";} } interface B { default String greet(){return "B";} } class C implements A, B {}`	No — when a class inherits two unrelated default methods with the same signature, the compiler refuses to guess which one wins ("class C inherits unrelated defaults"). `C` must explicitly override `greet()` (optionally delegating via `A.super.greet()`).

# 4. Misc Control Flow
What does this print? `outer: for (int i=0;i<3;i++){ for (int j=0;j<3;j++){ if (j==1) continue outer; System.out.print(i+""+j); } }`	`001020` — the labeled `continue outer` skips straight to the next iteration of the *outer* loop the moment `j==1`, so only the `j=0` case ever reaches the `print` for each value of `i`, giving `"00"`, `"10"`, `"20"` concatenated with no separators.
