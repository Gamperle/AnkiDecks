# 1. Collections
What happens here? `List<Integer> list = new ArrayList<>(List.of(1,2,3)); for (int i : list) { if (i == 2) list.remove(Integer.valueOf(2)); }`	Throws `ConcurrentModificationException` — the enhanced for-loop uses an `Iterator` under the hood, which tracks a modification count; mutating the backing list directly (not through the iterator) desyncs that count, and the *next* `hasNext()`/`next()` call detects it and fails fast. Fix: use `list.removeIf(i -> i == 2)` or `Iterator.remove()`.
What happens here? A mutable object is used as a `HashMap` key; after insertion, a field that participates in `hashCode()` is mutated on that same key object; then you call `map.get(sameKeyRef)`.	Usually returns `null` (the entry appears "lost") — the map computed the bucket from the *old* hash code at insertion time. After mutation, `get()` recomputes the hash from the *new* field value and looks in the wrong bucket, so it never finds the entry (which is still sitting in the old bucket). This is why keys should be immutable.
What is guaranteed about the iteration order of `HashMap`, `LinkedHashMap`, and `TreeMap`?	`HashMap`: unspecified and may even change between runs/JDK versions — never rely on it. `LinkedHashMap`: insertion order (or access order, if configured), always. `TreeMap`: sorted order per its `Comparator` (or natural ordering), always.
What happens here? `List.of(1,2,3).add(4);`	Throws `UnsupportedOperationException` — `List.of(...)` (Java 9+) returns a genuinely immutable list implementation, unlike `Arrays.asList(...)` (see below) or a plain `ArrayList`.
What happens here? `List<Integer> l = Arrays.asList(1,2,3); l.set(0, 99); l.add(4);`	`set(0, 99)` succeeds (and mutates the *original backing array* — `Arrays.asList` is a fixed-size *view* over the array you passed in), but `add(4)` throws `UnsupportedOperationException`, because the list's size can never change.
What happens here? `List<String> orig = new ArrayList<>(List.of("a")); List<String> view = Collections.unmodifiableList(orig); orig.add("b"); System.out.println(view);`	`[a, b]` — `unmodifiableList` only blocks writes made *through the wrapper itself* (`view.add(...)` would throw). It's a thin read-only view, not a deep copy, so changes to the underlying `orig` list are still visible through `view`.
What happens here? `Optional.of(null);` vs `Optional.ofNullable(null);`	`Optional.of(null)` throws `NullPointerException` immediately — it's documented to require a non-null value. `Optional.ofNullable(null)` returns `Optional.empty()` safely. Mixing these up is a common source of surprise NPEs.

# 2. Concurrency
What is guaranteed about the final value here? `int[] counter = {0}; Runnable inc = () -> { for (int i=0;i<100_000;i++) counter[0]++; }; run inc concurrently on two threads, then join both, then print counter[0].`	Only that it will be **at most** 200,000 — it is *not* guaranteed to equal 200,000, and in practice usually won't. `counter[0]++` is a read-modify-write of three separate steps (read, add, write) with no synchronization, so the two threads can race and clobber each other's updates ("lost update").
Does marking the counter `volatile` fix the race above?	No — `volatile` only guarantees *visibility* (every thread sees the latest write immediately) and ordering, not *atomicity*. `counter++` is still three separate operations even on a `volatile` field, so concurrent increments can still be lost. You need `AtomicInteger`, a lock, or `synchronized` to make the whole read-modify-write atomic.
What happens here? Thread 1 does `synchronized(A){ synchronized(B){...} }`; Thread 2 does `synchronized(B){ synchronized(A){...} }`; both run concurrently.	Can deadlock — if Thread 1 acquires `A` and Thread 2 acquires `B` at the same moment, each then blocks forever waiting for the lock the other already holds. Consistent lock ordering across all code paths is the standard fix.
Can a thread that already holds an object's intrinsic lock call another `synchronized` method on that same object without blocking itself?	Yes — Java's intrinsic locks (`synchronized`) are **reentrant**: the owning thread can re-acquire the same monitor any number of times (each acquisition incrementing an internal hold count), which is exactly what makes it safe for a `synchronized` method to call another `synchronized` method on `this`.
